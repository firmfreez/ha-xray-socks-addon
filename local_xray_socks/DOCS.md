## Обновление до 0.8.0: AnyConnect, уведомления и переподключение

Обновите установленный аддон и перезапустите его. Новая версия включает доступ
к Home Assistant Core API для получения телефонов и отправки уведомлений.
Существующие профили сохраняются: переподключение по умолчанию включено
без лимита, уведомления выключены.

### Диагностика входа AnyConnect (0.8.3)

При незавершённом входе проверьте строки `AnyConnect form`, `AnyConnect field`
и `AnyConnect form result` в журнале. Они показывают идентификатор формы,
название и тип видимых полей, наличие сообщения об ошибке (без текста)
и результат обработки формы. Значения полей, скрытые inputs, cookies и
содержимое страницы не выводятся. Это позволяет определить точное поле MFA
без сохранения сетевой трассировки. Запрос `main:password` сам по себе не
доказывает MFA: он может означать повторный первичный вход.
`result=2` — смена группы, `result=0` — готовность отправить форму, а не
подтверждение успешного входа. `AnyConnect field ready` показывает только
наличие заполненного поля, без значения. Повтор полной формы логина/пароля
останавливается до новой отправки; всего допускается до восьми callbacks.
Сохранённая настройка MFA `main:password` игнорируется: удалите её из профиля.

В версии 0.8.4 клиент явно отправляет `User-Agent: AnyConnect`. Некоторые
Cisco-шлюзы возвращают 404 для прежнего User-Agent OpenConnect; это известная
[проблема совместимости](https://gitlab.com/openconnect/openconnect/-/issues/602).
Прежняя диагностика через прямой шлюз не исключает этот фактор, поскольку
такой же заголовок передавался на обоих адресах. Используйте обычный адрес
сервера из Cisco, без пути `/+webvpn+/index.html`; редиректы поддерживаются.
Оставьте поле MFA пустым и выбранную группу входа. Не задавайте
`main:password=push`: это возвращает ответ в первичную форму, а не доказывает
переход к MFA. Успех входа проверяется на реальном сервере по появлению
push и установке туннеля, а не по одному `result=0`.

### Cisco AnyConnect

В VPN Manager добавьте профиль «Cisco AnyConnect (OpenConnect)», выберите порт,
введите адрес сервера, логин и пароль. При необходимости задайте группу входа.
Нажмите «Подключить» и подтвердите push на телефоне. Статус «Вход / ожидание MFA»
сохраняется до установки туннеля; время ожидания — до 3 минут.

В версии 0.8.1 пустое поле второго фактора включает ответы `push` для
стандартных полей `main:secondary_password`, `main:password2`,
`challenge:password` и `challenge:answer`. Если нужен другой идентификатор, в дополнительных настройках укажите идентификатор
формы и поля (например `main:secondary_password` или `challenge:password`) и значение
`push`. Имена полей и значения зависят от настройки шлюза и MFA-провайдера;
уточните их у администратора. Для браузерного входа выберите SSO, как описано ниже.
Обязательная проверка устройства (HostScan / posture) не реализована.
Ошибки авторизации/сертификата прекращают автоповторы; исправьте настройки
и подключите профиль вручную. Проверка TLS включена; для частного CA загрузите
сертификат и укажите его имя в дополнительных настройках.

#### Веб-вход SSO / SAML (0.9.0)

В 0.9.1 исправлен `ERR_NAME_NOT_RESOLVED` из-за прав доступа к сетевым
файлам браузера. Если ошибка возникла на 0.9.0, обновите аддон, отключите
профиль и подключите его снова, чтобы пересоздать файлы с исправленными правами.

В настройках AnyConnect выберите «Веб-вход SSO / SAML». Логин и пароль в профиле
для этого режима необязательны; автоматически они не отправляются. Сохраните
профиль, нажмите «Подключить», затем «Веб-вход SSO» на карточке подключения.

Окно показывает временный браузер внутри аддона. Проверьте адрес сайта входа,
нажмите нужное поле на изображении, введите текст под окном и нажмите «Ввести».
Для перехода между полями и отправки формы доступны Tab и Enter; для прокрутки
используйте колесо мыши. Подтвердите MFA на телефоне, если его запросит провайдер.
В 0.9.2 после выбора поля можно нажать «Вставить логин» или «Вставить пароль»:
аддон заменит содержимое выбранного поля сохранённым значением из профиля.
Чтобы сохранить эти данные, заполните логин и пароль в настройках профиля;
кнопка пароля не передаёт его в браузер панели Home Assistant. Перед вставкой
проверьте адрес сайта входа. Ввод с клавиатуры также доступен после клика на поле
в изображении. Действия выполняются по очереди с подтверждением браузера;
если поле не выбрано или браузер не отвечает, панель показывает ошибку.
На браузерный вход даётся 10 минут. После завершения OpenConnect получает
SSO-токен через свой публичный webview API; статус «Запущен» появляется только
после установки VPN-туннеля.

Окно доступно только через Home Assistant Ingress. Закрытие окна панели не
отменяет вход: его можно открыть снова. «Отключить» завершает попытку и удаляет
временные данные браузера. Cookies и введённые значения не включаются в журнал
или конфигурацию профиля. Chromium запускается отдельным непривилегированным
пользователем для каждого профиля. Корпоративный CA из профиля добавляется
в доверенные центры временного браузера; проверка TLS остаётся включённой.

Реализован SSO для встроенного веб-окна Cisco (`sso-v2`). Специальный режим
Cisco external-browser, FIDO/WebAuthn, аппаратные ключи, клиентские сертификаты
в браузере и проверки состояния устройства не поддерживаются. Совместимость
с корпоративным IdP нужно проверить на вашем сервере. После переподключения,
требующего новой авторизации, снова откройте SSO-окно; автоматического ввода
пароля и MFA нет. Для Chromium аддону требуется дополнительная память и место.

AnyConnect получает IPv4 DNS от сервера; поле корпоративного DNS позволяет
задать его вручную. SOCKS5 TCP/UDP и DNS-порт работают как у других рабочих VPN.
Для контроля связи задайте внутренний сайт, доступный через VPN.

### Переподключение и push для каждого профиля

- «Переподключаться при отключении»: выключить или включить автоматические повторы.
- «Сколько раз»: Всегда или 1–1000 повторов после первоначальной попытки.
  Пауза увеличивается от 5 секунд до 5 минут. Успешная проверка связи сбрасывает
  лимит; без проверочного сайта для рабочего VPN — 2 минуты работы процесса.
- «Отправлять push при отключении»: включите и выберите телефоны из списка.
  Доступны сервисы `notify.mobile_app_*` приложения Home Assistant Companion.
  Настройка и выбранные телефоны сохраняются отдельно для каждого VPN.

Уведомление содержит имя VPN и причину сбоя. Оно отправляется один раз за
эпизод недоступности, включая неудачный запуск, а не на каждый повтор. После
восстановления связи следующий сбой снова вызовет уведомление. Ручное
отключение и штатная остановка аддона не отправляют push. Ошибка доставки
попадает в журнал и не блокирует восстановление VPN. Без проверочного сайта
менеджер определяет отключение по завершению процесса; у AnyConnect также
по сигналу отключения туннеля. Для обнаружения зависшего соединения настройте
сайт и включите проверки: три неудачные проверки вызывают отключение и
восстановление согласно настройкам профиля.

При повторном входе AnyConnect сервер может снова прислать MFA-push: его
нужно подтвердить на телефоне. Режим «Всегда» может повторять такие запросы;
для ручного восстановления выключите переподключение или ограничьте попытки.

# Local Xray SOCKS 0.7.8 — обновление с общей панелью VPN

Это **обновление существующего аддона**, а не второй аддон. Каталог и slug
`local_xray_socks` сохранены. Панель VPN Manager открывается через HA Ingress.
Все четыре протокола — VLESS, AmneziaWG, OpenVPN, Check Point — доступны в ней.

## Как обновить

1. Сделайте резервную копию установленного Local Xray SOCKS в Home Assistant.
2. Используйте тот же репозиторий `https://github.com/firmfreez/ha-xray-socks-addon`,
   который уже добавлен в магазин HA. Версия обновления — **0.7.8**.
3. В магазине дополнений HA выберите «Проверить обновления», затем откройте
   **уже установленный Local Xray SOCKS** и нажмите «Обновить».
   Не удаляйте старый аддон и не устанавливайте копию через другой репозиторий:
   это другой экземпляр, и его `/data` не содержит ваших текущих настроек.
4. Для изолированных VPN требуются NET_ADMIN, SYS_ADMIN и TUN;
   AppArmor для этой экспериментальной реализации отключён. Если Supervisor
   требует выключить Protected mode для SYS_ADMIN, сделайте это в настройках
   **этого же аддона**. Host network, Docker socket и файлы HA Core не используются.
   Supervisor API используется для чтения старых настроек самого аддона при миграции.
5. После обновления включите «Показывать на боковой панели» и откройте Web UI.
   Сохранённые профили сохраняют свои порты; тип подключения не ограничивает выбор порта.
6. Затем добавьте OpenVPN / Check Point и проверьте рабочие сайты по шагам ниже.
   Настройте дополнительные порты в разделе «Сеть» аддона, если HA не назначил
   их автоматически при обновлении.

## Что происходит с прежними настройками

- На первом запуске импортируется сохранённая VLESS-ссылка и до четырёх
  конфигураций AmneziaWG. Прежний активный профиль получает слот 0 / порт 1080
  и автозапуск. Остальные профили импортируются выключенными.
- Настройки watchdog и уровня журнала сохраняются. Имена можно изменить в панели.
- Исходный `/data/options.json` не меняется. Его резервная копия сохраняется в
  `/data/vpn-manager/options-before-0.6.json` с правами 0600.
- Импорт выполняется один раз; после перезапуска удалённые профили не появляются
  снова, а исправленные настройки не заменяются старыми.
- **После импорта управляйте подключениями через Web UI.** Старые поля на вкладке
  «Конфигурация» оставлены для совместимости с обновлением, но не являются
  текущими настройками профилей. Их редактирование не переимпортирует данные.
- При неполном импорте панель покажет сообщение. Исходные настройки сохраняются;
  проверьте список, прежде чем запускать новые соединения.

## Добавление VLESS / AmneziaWG

Нажмите «Добавить VPN», выберите тип и свободный порт из списка 1080–1088.
Любой тип подключения можно назначить на любой свободный порт. Занятые порты
скрыты; при редактировании доступен также текущий порт профиля.

Для VLESS вставьте `vless://...`: поддерживаются TCP, WebSocket, gRPC, XHTTP,
HTTPUpgrade и mKCP; TLS, REALITY и отсутствие транспортного шифрования — в
совместимых сочетаниях Xray. Для AmneziaWG вставьте полный текст `[Interface]`
и `[Peer]`. Настройки из VLESS-ссылки сохраняются при формировании конфигурации.

Все подключения изолированы в собственных network namespaces и предоставляют
TCP/UDP SOCKS5 через Xray. Корпоративные DNS-порты предусмотрены для OpenVPN
и Check Point. При обновлении проверьте в разделе «Сеть» HA, что UDP-порты
выбранных подключений опубликованы: 1080–1088/udp.

Кнопка «Конфиг» показывает сохранённую ссылку или текст конфигурации. При
редактировании поля заполнены. Отдельные пароли сохраняются при пустом поле.
Старой формы с `protocol`, `link` и четырьмя AWG-профилями в настройках HA больше нет.

## Проверка подключения и журнал

Нажмите «Проверить подключение»: запрос выполняется через SOCKS выбранного VPN.
Результат, проверенный адрес, HTTP-код и время появляются в карточке.
VLESS/AmneziaWG по умолчанию проверяют интернет (Cloudflare/Google либо ваши
watchdog URL). В поле «Сайт для проверки подключения» можно указать другой адрес.
Для OpenVPN/Check Point укажите рабочий сайт один раз в профиле, например
`intranet.company.ru`. Адрес без схемы автоматически получает `https://`.
После запуска проверка выполняется автоматически и повторяется каждые 30 секунд.
Проверка сайта подтверждает HTTP-доступность; HTTP 401/403 также означает,
что сервер отвечает, но требует авторизацию или запрещает доступ.

«Запущен» означает, что процессы работают. Успех или ошибка проверки отображаются
отдельно, без постоянного сообщения «Доступность ещё не подтверждена».
Журнал открывается на последних строках; кнопка «↓ Вниз» возвращает к ним.
Автопрокрутка сохраняется, пока вы не прокрутите журнал вверх вручную.

## Что проверено

ARM64-образ успешно собран. Локально проверены миграция, сохранение и просмотр
конфигураций, свободные порты, статусы проверки и интерфейс в браузере.
В контейнере проверены TCP и UDP через SOCKS и синтетический туннель, блокировка
прямого выхода при потере туннеля, запуск Xray и userspace-интерфейса AmneziaWG.
Реальная авторизация на VPN-серверах и запуск на HA OS требуют проверки на устройстве.

## OpenVPN

1. В Tunnelblick найдите исходную конфигурацию через «VPN Details» и меню
   конфигурации / «Show in Finder». Названия пунктов зависят от версии.
   Пакет `.tblk` можно открыть как каталог; нужен `.ovpn` и связанные файлы.
2. В панели создайте профиль OpenVPN, выберите свободный порт (например, 1081), импортируйте
   `.ovpn`. Файлы `ca`, `cert`, `key`, `pkcs12`, `tls-auth` и т. п. загрузите в
   том же редакторе. В конфигурации должны быть **только имена файлов** без путей,
   например `ca company.pem`. Inline-блоки `<ca>`, `<cert>`, `<key>`, `<tls-crypt>`
   поддерживаются. Для закрытого ключа есть отдельное поле пароля.
3. Если есть `auth-user-pass`, введите логин/пароль. Однокнопочное подключение
   Tunnelblick может использовать пароль из связки ключей Mac: сам `.ovpn`
   не обязательно содержит его. Пароли вводятся только в вашей панели HA.
4. Оставьте поле DNS пустым: OpenVPN 2.7 автоматически применит IPv4 DNS,
   переданный сервером, и обновит его при переподключении. Активный DNS виден
   в карточке профиля. Если сервер не передаёт DNS, укажите корпоративный IPv4
   вручную (из журнала рабочего клиента или у администратора); ручное значение
   имеет приоритет. При отсутствии DNS запросы не уходят к публичным серверам.
5. Сохраните → Подключить → Журнал. Убедитесь, что OpenVPN завершил инициализацию,
   затем «Проверить сайт» с полным URL реального внутреннего сайта.

Поддерживается `dev tun`. Скрипты Tunnelblick/OpenVPN, плагины, вложенные config,
management-команды, произвольные файловые пути и `<connection>` намеренно
отклоняются. Если профиль не импортируется, сохраните текст ошибки: не удаляйте
непонятные директивы наугад. Настройки маршрутов из профиля и сервера действуют
только в окружении этого подключения.

## Check Point

1. Нужен экспортируемый личный сертификат **с закрытым ключом** в `.p12`/`.pfx`
   и его пароль, если установлен. Обычный `.cer` не заменяет этот файл.
2. Создайте профиль Check Point, выберите свободный порт и укажите адрес сервера.
   Для входа с сертификатом выберите **Personal Certificate**, загрузите `.p12`/`.pfx`
   и введите пароль файла. Логин и пароль учётной записи для этого режима не нужны.
   Для парольного входа выберите соответствующий способ и заполните логин/пароль.
3. Нажмите **Получить методы входа с сервера** и выберите подходящий метод.
   Можно оставить автоматический выбор: при подключении аддон выберет единственный
   подходящий вариант. Если вариантов несколько, потребуется выбрать вручную.
   Если нужен корпоративный CA, загрузите его в дополнительных файлах, укажите
   имя в дополнительных настройках и сохраните профиль перед запросом методов.
4. Оставьте корпоративный DNS пустым для получения DNS от сервера или укажите
   его вручную. Сохраните профиль, нажмите «Подключить», проверьте журнал и рабочий сайт.
5. По умолчанию новый профиль использует IPsec (UDP). Если UDP недоступен,
   попробуйте SSL в дополнительных настройках. IPsec использует userspace UDP
   transport, чтобы трафик SOCKS шёл через туннельный интерфейс и работала
   блокировка прямого выхода.

Check Point получает запись в `/proc/sys/net` только в собственных сетевом и
mount-пространствах профиля: это нужно для настройки туннеля snx-rs в HA OS.
Настройки сети контейнера и Home Assistant не изменяются. Предупреждение
об отсутствии D-Bus относится к мониторингу сети и само по себе не завершает VPN.

Для Check Point интерактивные MFA/SSO, аппаратные токены, enrollment и проверки
состояния рабочего устройства не реализованы в панели. CLI запускается без интерактивного ввода.
Если сервер требует такой шаг, возможна ошибка или ожидание; остановите профиль.
Поддержка методов самим snx-rs не означает поддержку этих сценариев этой панелью.

## Проверка до настройки Keenetic

С Mac, подставив адрес Raspberry Pi и рабочий URL:

```sh
curl --noproxy "" --proxy socks5h://192.168.1.50:1081 --max-time 15 https://internal.example
```

`socks5h` передаёт имя сайта SOCKS-серверу для разрешения через корпоративный DNS.
Не добавляйте `-k`: ошибка доверия HTTPS-сертификату — отдельная проблема,
а не доказательство отсутствия туннеля. Ответ 401/403 означает, что HTTP-сервер
доступен, но не подтверждает доступ к приложению. Панель сообщает код ответа.

Повторите для 1082. Запустите оба профиля одновременно и убедитесь, что каждый
открывает свой ресурс. Остановите один профиль и повторите запрос: он должен
перестать работать; второй профиль и личный VPN должны продолжить работу.
В контейнере проверена блокировка трафика при потере синтетического туннеля.
Восстановление реального VPN отдельно проверьте на устройстве.

## Keenetic и DNS

Создайте два подключения к SOCKS5: `IP_RASPBERRY:1081` и `IP_RASPBERRY:1082`
(либо порты, назначенные в HA). Используйте их в уже знакомой схеме маршрутизации
для соответствующих рабочих адресов. Начните с одного тестового устройства.

**Настройка DNS внутри профиля решает DNS только для запросов, переданных в SOCKS
с именем.** Если Keenetic сначала разрешает домен сам и отправляет SOCKS уже IP,
нужна отдельная настройка DNS на Keenetic/AdGuard Home. Каждый профиль публикует
DNS-forwarder (UDP и TCP): слот 1 — порт 10531, слот 2 — 10532, затем 10533/10534.
Его запросы идут к указанным в профиле корпоративным DNS через соответствующий VPN.
Правила Keenetic аддон не меняет. Успешный curl с socks5h ещё не доказывает работу доменов через
прозрачную маршрутизацию роутера. Если используется AdGuard Home, добавьте условные upstream-серверы:

```text
[/work-one.example/]192.168.1.50:10531
[/work-two.example/]192.168.1.50:10532
```

Подставьте реальные зоны и адрес Raspberry Pi; клиенты должны использовать этот
AdGuard Home как DNS. Для каждой зоны выберите только её VPN-forwarder, без
публичного fallback. DNS-forwarder сначала использует UDP к корпоративному DNS на порту 53;
при усечённом ответе или недоступности UDP пробует TCP. Для проверки можно временно использовать
SOCKS непосредственно в браузере с удалённым разрешением DNS.

Автоматический fallback рабочих маршрутов на обычный интернет на Keenetic
настраивайте отдельно: блокировка в аддоне не контролирует выбор роутера.
Совпадающие IP в двух компаниях нельзя различить одним маршрутом назначения.

## Ограничения и хранение

- До девяти профилей, каждый со своим портом 1080–1088 и поддержкой TCP/UDP.
  SOCKS не передаёт ICMP и не заменяет полноценную LAN-маршрутизацию.
  IPv6-маршрутизация корпоративных туннелей пока не проверена; корпоративный DNS
  настраивается IPv4-адресами. Поддержка функций авторизации зависит от VPN-клиента и сервера.
- SOCKS-порты без аутентификации предназначены для доверенной LAN. DNS-forwarder также доступен из LAN. Не публикуйте
  эти порты в интернет; при необходимости ограничьте доступ правилами роутера.
- Для namespaces зарезервированы `10.253.0.0/30` … `10.253.8.0/30`. Если эти
  диапазоны используются в рабочих сетях, адресацию нужно изменить в runtime.
- Профили запускаются и восстанавливаются независимо. После ошибки DNS или
  завершения процесса повтор выполняется через 5, 10, 20, 40, 80, 160 и далее
  каждые 300 секунд. После двух минут работы пауза сбрасывается. Кнопка
  «Отключить» отменяет повторы; перезапуск всего аддона не требуется.
- VLESS/AmneziaWG сохраняют собственный watchdog. OpenVPN/Check Point
  переподключаются после трёх неудачных проверок указанного рабочего сайта.
  Выбирайте постоянно доступный внутренний адрес: недоступность самого сайта
  также вызывает переподключение. Без этого адреса контролируется завершение
  процессов, но не зависший туннель. Распознанная ошибка авторизации или
  сертификата останавливает автоповторы до исправления настроек и ручного запуска.
- Ошибка DNS указывается вместе с именем VPN-сервера; поиск адреса ограничен
  12 секундами на имя. Корпоративные DNS-запросы не переключаются на публичные
  резолверы. При общем сбое интернета восстановление начнётся после возврата связи.
- Журналы ограничены 250 строками в памяти, известные пароли маскируются.
  Адреса серверов и рабочие домены могут присутствовать. Debug/trace не включаются.
- Профили и сертификаты лежат в `/data/vpn-manager`, файлы имеют режим 0600.
  Это не шифрование: администратор HA и резервные копии имеют доступ к секретам.
- Пустые поля паролей сохраняют прежние значения; есть явный флажок очистки.
  Чтобы удалить старые загруженные файлы, удалите профиль целиком и создайте заново.

## Разработка

```sh
python3 -B -m unittest discover -s tests -v
docker build --platform linux/arm64 --build-arg BUILD_ARCH=aarch64 --build-arg BUILD_VERSION=0.7.6 -t local-xray-socks:0.7.6 local_xray_socks
```

Основной образ остаётся Home Assistant Alpine. Check Point использует неизменённый
ARM64 snx-rs 6.4.1 (AGPL-3.0), SHA256 проверяется при сборке. Для него добавлен
приватный glibc loader из Debian, не заменяющий системную libc Alpine. Сборка
проверяет `snx-rs --version` и в исходном слое Debian, и через launcher в Alpine.

Исходники и лицензия snx-rs: https://github.com/ancwrd1/snx-rs/tree/v6.4.1
Документация HA: https://developers.home-assistant.io/docs/apps/configuration/
OpenVPN: https://openvpn.net/community-docs/community-articles/openvpn-2-6-manual.html
AdGuard DNS: https://github.com/AdguardTeam/AdGuardHome/wiki/Configuration
