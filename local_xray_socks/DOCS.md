# Local Xray SOCKS 0.7.1 — обновление с общей панелью VPN

Это **обновление существующего аддона**, а не второй аддон. Каталог и slug
`local_xray_socks` сохранены. Панель VPN Manager открывается через HA Ingress.
Все четыре протокола — VLESS, AmneziaWG, OpenVPN, Check Point — доступны в ней.

## Как обновить

1. Сделайте резервную копию установленного Local Xray SOCKS в Home Assistant.
2. Используйте тот же репозиторий `https://github.com/firmfreez/ha-xray-socks-addon`,
   который уже добавлен в магазин HA. Версия обновления — **0.7.1**.
3. В магазине дополнений HA выберите «Проверить обновления», затем откройте
   **уже установленный Local Xray SOCKS** и нажмите «Обновить».
   Не удаляйте старый аддон и не устанавливайте копию через другой репозиторий:
   это другой экземпляр, и его `/data` не содержит ваших текущих настроек.
4. Для изолированных VPN требуются NET_ADMIN, SYS_ADMIN и TUN;
   AppArmor для этой экспериментальной реализации отключён. Если Supervisor
   требует выключить Protected mode для SYS_ADMIN, сделайте это в настройках
   **этого же аддона**. Host network, Docker socket и файлы HA Core не используются.
   Supervisor API используется для чтения старых настроек самого аддона при миграции.
5. После обновления включите «Показывать на боковой панели» и откройте Web UI.
   Сохранённые профили сохраняют свои порты; тип подключения не ограничивает выбор порта.
6. Затем добавьте OpenVPN / Check Point и проверьте рабочие сайты по шагам ниже.
   Настройте дополнительные порты в разделе «Сеть» аддона, если HA не назначил
   их автоматически при обновлении.

## Что происходит с прежними настройками

- На первом запуске импортируется сохранённая VLESS-ссылка и до четырёх
  конфигураций AmneziaWG. Прежний активный профиль получает слот 0 / порт 1080
  и автозапуск. Остальные профили импортируются выключенными.
- Настройки watchdog и уровня журнала сохраняются. Имена можно изменить в панели.
- Исходный `/data/options.json` не меняется. Его резервная копия сохраняется в
  `/data/vpn-manager/options-before-0.6.json` с правами 0600.
- Импорт выполняется один раз; после перезапуска удалённые профили не появляются
  снова, а исправленные настройки не заменяются старыми.
- **После импорта управляйте подключениями через Web UI.** Старые поля на вкладке
  «Конфигурация» оставлены для совместимости с обновлением, но не являются
  текущими настройками профилей. Их редактирование не переимпортирует данные.
- При неполном импорте панель покажет сообщение. Исходные настройки сохраняются;
  проверьте список, прежде чем запускать новые соединения.

## Добавление VLESS / AmneziaWG

Нажмите «Добавить VPN», выберите тип и свободный порт из списка 1080–1088.
Любой тип подключения можно назначить на любой свободный порт. Занятые порты
скрыты; при редактировании доступен также текущий порт профиля.

Для VLESS вставьте `vless://...`: поддерживаются TCP, WebSocket, gRPC, XHTTP,
HTTPUpgrade и mKCP; TLS, REALITY и отсутствие транспортного шифрования — в
совместимых сочетаниях Xray. Для AmneziaWG вставьте полный текст `[Interface]`
и `[Peer]`. Настройки из VLESS-ссылки сохраняются при формировании конфигурации.

Все подключения изолированы в собственных network namespaces и предоставляют
TCP/UDP SOCKS5 через Xray. Корпоративные DNS-порты предусмотрены для OpenVPN
и Check Point. При обновлении проверьте в разделе «Сеть» HA, что UDP-порты
выбранных подключений опубликованы: 1080–1088/udp.

Кнопка «Конфиг» показывает сохранённую ссылку или текст конфигурации. При
редактировании поля заполнены. Отдельные пароли сохраняются при пустом поле.
Старой формы с `protocol`, `link` и четырьмя AWG-профилями в настройках HA больше нет.

## Проверка подключения и журнал

Нажмите «Проверить подключение»: запрос выполняется через SOCKS выбранного VPN.
Результат, проверенный адрес, HTTP-код и время появляются в карточке.
VLESS/AmneziaWG по умолчанию проверяют интернет (Cloudflare/Google либо ваши
watchdog URL). В поле «Сайт для проверки подключения» можно указать другой адрес.
Для OpenVPN/Check Point укажите рабочий сайт один раз в профиле, например
`intranet.company.ru`. Адрес без схемы автоматически получает `https://`.
После запуска проверка выполняется автоматически и повторяется каждые 30 секунд.
Проверка сайта подтверждает HTTP-доступность; HTTP 401/403 также означает,
что сервер отвечает, но требует авторизацию или запрещает доступ.

«Запущен» означает, что процессы работают. Успех или ошибка проверки отображаются
отдельно, без постоянного сообщения «Доступность ещё не подтверждена».
Журнал открывается на последних строках; кнопка «↓ Вниз» возвращает к ним.
Автопрокрутка сохраняется, пока вы не прокрутите журнал вверх вручную.

## Что проверено

ARM64-образ успешно собран. Локально проверены миграция, сохранение и просмотр
конфигураций, свободные порты, статусы проверки и интерфейс в браузере.
В контейнере проверены TCP и UDP через SOCKS и синтетический туннель, блокировка
прямого выхода при потере туннеля, запуск Xray и userspace-интерфейса AmneziaWG.
Реальная авторизация на VPN-серверах и запуск на HA OS требуют проверки на устройстве.

## OpenVPN

1. В Tunnelblick найдите исходную конфигурацию через «VPN Details» и меню
   конфигурации / «Show in Finder». Названия пунктов зависят от версии.
   Пакет `.tblk` можно открыть как каталог; нужен `.ovpn` и связанные файлы.
2. В панели создайте профиль OpenVPN, выберите свободный порт (например, 1081), импортируйте
   `.ovpn`. Файлы `ca`, `cert`, `key`, `pkcs12`, `tls-auth` и т. п. загрузите в
   том же редакторе. В конфигурации должны быть **только имена файлов** без путей,
   например `ca company.pem`. Inline-блоки `<ca>`, `<cert>`, `<key>`, `<tls-crypt>`
   поддерживаются. Для закрытого ключа есть отдельное поле пароля.
3. Если есть `auth-user-pass`, введите логин/пароль. Однокнопочное подключение
   Tunnelblick может использовать пароль из связки ключей Mac: сам `.ovpn`
   не обязательно содержит его. Пароли вводятся только в вашей панели HA.
4. Впишите IPv4 корпоративного DNS (можно посмотреть в журнале текущего клиента
   или уточнить у администратора). Первая версия не импортирует pushed DNS
   автоматически. Без этого проверяйте ресурс по IP, учитывая HTTPS-сертификат.
5. Сохраните → Подключить → Журнал. Убедитесь, что OpenVPN завершил инициализацию,
   затем «Проверить сайт» с полным URL реального внутреннего сайта.

Поддерживается `dev tun`. Скрипты Tunnelblick/OpenVPN, плагины, вложенные config,
management-команды, произвольные файловые пути и `<connection>` намеренно
отклоняются. Если профиль не импортируется, сохраните текст ошибки: не удаляйте
непонятные директивы наугад. Настройки маршрутов из профиля и сервера действуют
только в окружении этого подключения.

## Check Point

1. Нужен экспортируемый личный сертификат **с закрытым ключом** в `.p12`/`.pfx`
   и его пароль, если установлен. Обычный `.cer` не заменяет этот файл.
2. Создайте профиль Check Point, свободный слот (например, 2 / порт 1082), адрес сервера без `https://`.
   Начните с SSL. Загрузите сертификат и укажите его точное имя в соответствующем
   поле. Если сервер подписан корпоративным CA, загрузите PEM CA и укажите его
   имя; проверка сертификата сервера остаётся включённой.
3. Сохраните профиль с пустым Login type, нажмите **Методы входа**. Скопируйте
   подходящий идентификатор `vpn_...` в Login type через «Изменить» и сохраните.
   Выбирайте метод, соответствующий вашему сертификату/логину, а не случайный.
4. Укажите логин/пароль, если их требует выбранный метод. Укажите корпоративный
   DNS. Нажмите Подключить, проверьте журнал, затем внутренний сайт.
5. Если SSL не поддерживается шлюзом, остановите профиль, выберите IPsec и
   повторите проверку. IPsec использует userspace UDP transport, чтобы трафик
   SOCKS шёл через туннельный интерфейс и работала блокировка прямого выхода.

Интерактивные MFA/SSO, аппаратные токены, enrollment и проверки состояния рабочего
устройства не реализованы в панели. CLI запускается без интерактивного ввода.
Если сервер требует такой шаг, возможна ошибка или ожидание; остановите профиль.
Поддержка методов самим snx-rs не означает поддержку этих сценариев этой панелью.

## Проверка до настройки Keenetic

С Mac, подставив адрес Raspberry Pi и рабочий URL:

```sh
curl --noproxy "" --proxy socks5h://192.168.1.50:1081 --max-time 15 https://internal.example
```

`socks5h` передаёт имя сайта SOCKS-серверу для разрешения через корпоративный DNS.
Не добавляйте `-k`: ошибка доверия HTTPS-сертификату — отдельная проблема,
а не доказательство отсутствия туннеля. Ответ 401/403 означает, что HTTP-сервер
доступен, но не подтверждает доступ к приложению. Панель сообщает код ответа.

Повторите для 1082. Запустите оба профиля одновременно и убедитесь, что каждый
открывает свой ресурс. Остановите один профиль и повторите запрос: он должен
перестать работать; второй профиль и личный VPN должны продолжить работу.
В контейнере проверена блокировка трафика при потере синтетического туннеля.
Восстановление реального VPN отдельно проверьте на устройстве.

## Keenetic и DNS

Создайте два подключения к SOCKS5: `IP_RASPBERRY:1081` и `IP_RASPBERRY:1082`
(либо порты, назначенные в HA). Используйте их в уже знакомой схеме маршрутизации
для соответствующих рабочих адресов. Начните с одного тестового устройства.

**Настройка DNS внутри профиля решает DNS только для запросов, переданных в SOCKS
с именем.** Если Keenetic сначала разрешает домен сам и отправляет SOCKS уже IP,
нужна отдельная настройка DNS на Keenetic/AdGuard Home. Каждый профиль публикует
DNS-forwarder (UDP и TCP): слот 1 — порт 10531, слот 2 — 10532, затем 10533/10534.
Его запросы идут к указанным в профиле корпоративным DNS через соответствующий VPN.
Правила Keenetic аддон не меняет. Успешный curl с socks5h ещё не доказывает работу доменов через
прозрачную маршрутизацию роутера. Если используется AdGuard Home, добавьте условные upstream-серверы:

```text
[/work-one.example/]192.168.1.50:10531
[/work-two.example/]192.168.1.50:10532
```

Подставьте реальные зоны и адрес Raspberry Pi; клиенты должны использовать этот
AdGuard Home как DNS. Для каждой зоны выберите только её VPN-forwarder, без
публичного fallback. DNS-forwarder использует TCP к корпоративному DNS на порту 53;
этот трафик должен быть разрешён рабочим VPN. Для проверки можно временно использовать
SOCKS непосредственно в браузере с удалённым разрешением DNS.

Автоматический fallback рабочих маршрутов на обычный интернет на Keenetic
настраивайте отдельно: блокировка в аддоне не контролирует выбор роутера.
Совпадающие IP в двух компаниях нельзя различить одним маршрутом назначения.

## Ограничения и хранение

- До девяти профилей, каждый со своим портом 1080–1088 и поддержкой TCP/UDP.
  SOCKS не передаёт ICMP и не заменяет полноценную LAN-маршрутизацию.
  IPv6-маршрутизация корпоративных туннелей пока не проверена; корпоративный DNS
  настраивается IPv4-адресами. Поддержка функций авторизации зависит от VPN-клиента и сервера.
- SOCKS-порты без аутентификации предназначены для доверенной LAN. DNS-forwarder также доступен из LAN. Не публикуйте
  эти порты в интернет; при необходимости ограничьте доступ правилами роутера.
- Для namespaces зарезервированы `10.253.0.0/30` … `10.253.8.0/30`. Если эти
  диапазоны используются в рабочих сетях, адресацию нужно изменить в runtime.
- Автозапуск профиля есть. VLESS/AmneziaWG сохраняют прежний watchdog с проверкой
  URL и восстановлением. Для OpenVPN/Check Point отдельного watchdog и
  автоматического перезапуска завершившегося клиента пока нет. Внутренние reconnect механизмы клиентов могут
  работать; после завершения процесса профиль останавливается с ошибкой.
- Журналы ограничены 250 строками в памяти, известные пароли маскируются.
  Адреса серверов и рабочие домены могут присутствовать. Debug/trace не включаются.
- Профили и сертификаты лежат в `/data/vpn-manager`, файлы имеют режим 0600.
  Это не шифрование: администратор HA и резервные копии имеют доступ к секретам.
- Пустые поля паролей сохраняют прежние значения; есть явный флажок очистки.
  Чтобы удалить старые загруженные файлы, удалите профиль целиком и создайте заново.

## Разработка

```sh
python3 -B -m unittest discover -s tests -v
docker build --platform linux/arm64 --build-arg BUILD_ARCH=aarch64 --build-arg BUILD_VERSION=0.7.1 -t local-xray-socks:0.7.1 local_xray_socks
```

Основной образ остаётся Home Assistant Alpine. Check Point использует неизменённый
ARM64 snx-rs 6.4.1 (AGPL-3.0), SHA256 проверяется при сборке. Для него добавлен
приватный glibc loader из Debian, не заменяющий системную libc Alpine. Сборка
проверяет `snx-rs --version` и в исходном слое Debian, и через launcher в Alpine.

Исходники и лицензия snx-rs: https://github.com/ancwrd1/snx-rs/tree/v6.4.1
Документация HA: https://developers.home-assistant.io/docs/apps/configuration/
OpenVPN: https://openvpn.net/community-docs/community-articles/openvpn-2-6-manual.html
AdGuard DNS: https://github.com/AdguardTeam/AdGuardHome/wiki/Configuration
